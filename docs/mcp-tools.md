# MCP tools

MCP clients launch the `mcp` command over stdio. The [agent workflow](workflow.md) gives the sequence of calls that builds a packet, and the server sends a short form of it as its MCP instructions. By default the server offers the three tools that workflow uses: `context_builder` starts a build, `context_job` waits for, inspects, cancels or disposes of a build's job, and `context_prepare` publishes a saved packet with its final task. Set `tools` to `"full"` in the configuration, or start the server with `mcp --tools full`, to add the workspace tools `workspace_declare`, `workspace_refresh` and `workspace_close`; the exploration tools `get_file_tree`, `get_code_structure`, `file_search`, `read_file` and `git`; and the manual-packet tools `prompt`, `manage_selection`, `draft_create`, `draft_inspect`, `draft_update`, `draft_validate`, `draft_finalize` and `draft_dispose`. The three core tools are the same in both sets. `tools/list` supplies their schemas. Each result is one text block of compact JSON; `get_code_structure` instead returns its rendered view as text, with the complete evidence as structured content.

## The workspace argument

`context_builder` and `context_prepare` each take a `workspace`: `{ "roots": [{ "name": "app", "absolutePath": "/abs/app" }], "outputRoot": "/abs/app/prompt-exports" }`, with optional `exclusions`. The output directory must already exist and is never indexed. The server opens and indexes each distinct workspace once per connection and keeps that index for later calls, so send the same workspace each time rather than varying it. Give each project one output directory and a distinct `outputName` for each bundle; a new output directory starts a separate workspace, whose first refresh reads every file again. Job, draft and workspace IDs belong to the connected client and end with the connection.

## Starting a build: `context_builder`

`context_builder` takes the `workspace`, a `purpose` (`planning`, `review` or `investigation`), the `task` and a new `outputName`. Optional inputs add evidence the packet must contain. `required` lists files as `{ "root": "app", "path": "docs/plan.md" }`; add `lines: [{ "start": 10, "end": 40 }]` to deliver one-based inclusive ranges instead of the whole file. `patches` lists complete local Git comparisons as `{ id, root, comparison, paths }`, where `comparison` is `{ "kind": "worktree", "base": "HEAD", "includeUntracked": true }`, `{ "kind": "staged", "base": "HEAD" }` or `{ "kind": "commits", "base": "main", "target": "HEAD" }`, and omitted `paths` cover the whole comparison. `documents` carries text from outside the roots as `{ id, role, origin, text }`, with `role` set to `plan`, `report` or `evidence`. `copyPreset` is `standard` or `codeReview` and defaults to `codeReview` for a review or any patch. Omitted `budgetUnits` and `enhancementMode` take the host defaults. `discovery: { "model": "provider/model", "thinking": "low" }` selects the discovery model from the configured model and `discovery.allowedModels`, and its thinking level; either field can be omitted to keep the configured value. Another model fails with `modelNotAllowed` and a message listing the allowed models, before any work starts, and a level the model does not support fails the job with `unsupportedThinkingLevel` before any model request; the receipt's `discovery.thinkingLevels` then lists the levels the model supports, and `discovery.requested` always shows the model and level the job ran with. `clarification` lets discovery ask the user questions. Discovery starts from an empty selection with automatic code maps, empty constraints and no hints. Library hosts, the `build` command and `draft_create` take the full context request shown under [Manual context packets](packets.md#drafts), which also sets those fields.

The output directory and `outputName` identify a build within the connection. Repeating a start with the same workspace, request and discovery settings returns the same job, including one that has finished, failed or been disposed; the same `outputName` with a different request, workspace or discovery settings fails with `outputNameConflict`. Omitted settings count as the defaults they resolve to. When `outputName` already names a file, directory or symlink in the output directory, the job fails with `alreadyExists` before discovery begins. A new attempt therefore needs a new `outputName`.

## Following a job: `context_job`

Wait with `context_job` and `{ "op": "wait", "jobId": "...", "durationMs": 10000 }`; `durationMs` belongs to `wait` only, and timeout or cancellation of that wait leaves the job running. A pending clarification question arrives in a wait's reply: as a form when the client supports MCP forms, otherwise as `question`, with an `id`, a `message` and a JSON `schema` keyed by question ID. Ask the user, then answer with `{ "op": "answer", "jobId": "...", "questionId": "...", "response": { "action": "accept", "content": { "<question id>": "answer" } } }`, or `"response": { "action": "decline" }` to skip; discovery continues with the answer. If nobody answers before the question's timeout, 300 seconds unless the build sets another, discovery continues without the answer. `"op": "status"` returns the snapshot without waiting or delivering a question. `"op": "cancel"` cancels the job. `"op": "dispose"` cancels or joins the job and deletes its Git snapshots; its receipt and saved packet remain. Closing the connection or runtime cancels and joins active work, and the server forgets the connection's jobs. A claimed publication finishes before shutdown returns.

## Receipts

A ready job snapshot's `bundle` is a bundle receipt rather than the manifest. It gives the bundle `directory`, the `context.md` path and identity, the accounting, one entry per delivered material (representation, path or ID, origin and estimated units), omitted sources and the resulting prompt. `draft_finalize` returns the same receipt without the prompt. `context_prepare` returns it with `added` and `removed` entries, relative to the saved bundle, in place of the complete material list. Ready and blocked snapshots give the number of discovery completions, their summed token `usage` (`input`, `output`, `cacheRead` and `cacheWrite`, as the provider reports them) and `toolCalls`, the number of calls the model made to each tool; each completion matched the effective model, or the job would have failed. Failed and cancelled snapshots keep the complete completion records, each with its own `usage` and `toolCalls`. Calls made inside a `codemode` script are not counted. The complete `manifest.json` stays in the bundle directory.

The terminal receipt separates requested, locally dispatched, SDK-reported and independently returned model identities. It records the prompt hash, `buildLockSHA256`, the effective model record and thinking/recovery policy, ordinary and summary completions with their token usage, and local settlement. `buildLockSHA256` identifies mipmux's build lockfile; audit the installed graph separately when deploying a local package. Endpoint and header values are represented by hashes rather than copied into the receipt. Codex's independent server identity is unavailable; provider-internal attempts may be unobserved. Local closure does not establish remote cancellation or billing cessation. Only a verified ready bundle is transferable context. See [the context protocol](context-protocol.md) for delivery and receipt capture.

## Preparing the final packet: `context_prepare`

`context_prepare` publishes a new bundle from a saved one with a replacement prompt and makes no model call. It takes the `workspace`, `bundle` (the saved bundle directory relative to the output directory), `prompt` (the complete final task, delivered verbatim as user instructions in place of the saved prompt) and a new `outputName`, which fails with `alreadyExists` when the output directory already has an entry by that name. The workspace must name the roots and output directory that built the bundle. mipmux reads the saved files through its native reader, which refuses symlinks and paths outside the output root. It verifies the bundle, checks its evidence against current files, and repeats that check before publishing the new manifest. The new bundle keeps the saved evidence, constraints and formatting. When only the prompt changes, the saved budget does not limit the packet: its allowance rises as far as the new prompt needs. A `budgetUnits` value sets a budget the packet must fit instead, and a packet over it returns `blocked` with `overBudget`. A changed file fails with `sourceChanged` and its path. Ready replies are bundle receipts.

Set `refresh: true` to rebuild the packet from current files instead, with the same selection, required inputs and preset. Adding `required`, `documents` or `patches`, in the forms `context_builder` takes, also rebuilds it. A rebuild reads files the way draft finalization does and makes no model call.

`remove` and `demote` trim the packet and also rebuild it. Each takes material paths as receipts list them: `root/path` for a file, or a Git artifact's alias. `remove` drops optional files and Git artifacts. `demote` replaces optional full files and slices with their codemaps. As with demotion in `manage_selection`, automatic codemaps stay on, so only the automatic codemaps that the demoted files alone referenced drop out and appear under `removed`. Required material cannot be removed or demoted. A path that names no saved material, appears twice, or names material these edits cannot change returns `invalidSelection`, which lists each problem.

A bundle keeps its selected Git artifacts unless `remove` names them. Each artifact is a diff captured at discovery, so while any remain, other edits require the saved evidence to still match current files, and `refresh: true` returns `refreshRequiresDiscovery`. Changed code under review needs a new Context Builder run.

## Exploration tools

In the full set, `workspace_declare` returns the workspace ID that the exploration and manual-packet tools take. Exploration calls use `workspaceId` and a tool-specific `input`. Request a file tree with only `{ "workspaceId": "..." }`, read with `{ "workspaceId": "...", "input": { "root": "app", "path": "src/main.ts" } }`, or search with `{ "workspaceId": "...", "input": { "query": { "text": "greet" } } }`. These tools, in the full set, are available independently of context-builder jobs.

File trees use RepoPrompt CE's renderer. `type: "roots"` lists physical roots; `type: "files"` supports `mode: "auto"`, `"full"`, `"folders"` or `"selected"`. The default is files in automatic mode. To inspect a directory, supply `scope: { root: "repo", directory: { kind: "descendant", path: "src" } }`; use `{ kind: "root" }` for a whole named root. `maxDepth` starts at folder depth zero and retains selected descendants beyond the cutoff. A star marks selected implementation and a plus marks available code-map structure. Selected mode requires an owned manual `draftId`. Tree pages contain complete rendered lines; follow `continuation` to obtain the rest.

Git queries use the configured Git executable. For status, log, show and blame, select checkouts with `repositories: [{ root: "repo" }]`. Add a selector's root-relative `path` to target a nested repository, or its absolute `worktree` to select an advertised same-repository checkout after identity checks. A declared subroot resolves its owning checkout. Selectors retain their order and deduplicate checkouts; status returns one result per checkout, while history operations use the first checkout and warn when multiple were selected. Linked-worktree results include checkout metadata and warnings.

Call `git` with `input: { op: "status", repositories: [{ root: "repo" }] }` for branch/tracking metadata and sorted staged, modified and untracked paths. Use `op: "log"` for the latest ten commits; `count` and an operation-level `path` restrict history. Use `input: { op: "blame", repositories: [{ root: "repo" }], path: "src/main.ts", lines: "1-20" }` for line attribution. Log/blame paths are relative to the declared root for a plain selector, or to the chosen checkout for a nested-repository/worktree selector. File paths remain subject to workspace policy. Use `op: "show", ref: "HEAD", detail: "full"` with the same selector for commit metadata, file statistics and complete patch hunks. `detail` defaults to `"summary"`; `"files"` includes per-file statistics, and `"patches"` requests the same complete hunks as `"full"`. Log, blame and show disable Git's textconv path. Status can execute repository-local clean/process filters, so use trusted repository Git configurations. The complete reply must fit `maxOutputBytes`.

Without `repositories`, workspace calls use the first declared root that resolves to a checkout. Calls owned by a draft instead use its initially elected checkouts: status can inspect all of them, while log, show and blame require an explicit selector when several were elected. An empty or unavailable initial target requires explicit selectors.

Use `input: { op: "diff", root: "repo", compare: "uncommitted", detail: "full" }` to inspect changes across the owning checkout. Staged, unstaged, revision and merge-base comparisons are supported. Optional `path`/`paths` accept checkout-relative Git globs and exclusions or absolute literal paths. Optional `worktree` selects an advertised same-repository checkout after identity checks. Protected endpoints are omitted and listed in `exclusions`; ordinary file tools remain scoped to declared roots. Diff compares captured source bytes in a private worktree. Git configuration must be trusted because clean/process filters may execute programs.

Reads default to the whole file. Structure requires `seeds` and defaults to `expand: "none"` and depth 1. Search defaults to automatic mode and regex inference, case-insensitive matching, no filters, zero surrounding context, and snippets rather than count-only output. Use `query.kind: "literal"` to select literal interpretation, `query.kind: "regex"` for PCRE2 or `query.kind: "glob"` for path globs; glob searches select path mode. Omit `continuation` for the first page.

Structural queries use the owned draft's full/sliced selection when `seeds` is omitted; supply `draftId` beside `input` in MCP. Explicit `seeds` accepts up to 256 file or directory selectors. Files use `{ kind: "file", root: "repo", path: "src/main.ts" }`; directories use `{ kind: "directory", root: "repo", directory: { kind: "root" } }` or a descendant directory reference. Queries accept optional `expand: "uses"`, `"used_by"` or `"both"`, and `depth` from 1 to 4. `signatures` defaults to `true`; `size` defaults to `"medium"` and also accepts `"small"` or `"large"`. Results include root-local graph evidence, unresolved references, seed/index states and admitted signatures. Text responses use RepoPrompt CE's graph and signature presentation; structured MCP results retain all returned evidence. `summary.tokens` counts admitted signatures and separators.

MCP puts optional `maxOutputBytes` beside `input`; omitted caps use the host default. Draft inspection/update calls use `draftId` and `input` with the same outer cap. The byte limit covers the serialized result, including the structured content of a structure query. The small `outputBudgetTooSmall` control diagnostic is the documented cap exception. Pi discovery-agent exploration uses the same input defaults and requires an explicit `maxOutputBytes` inside its input.

## Manual-packet tools

The tools `prompt`, `manage_selection`, `draft_create`, `draft_inspect`, `draft_update`, `draft_validate`, `draft_finalize` and `draft_dispose` select a packet's contents without discovery. [Manual context packets](packets.md) describes them.
