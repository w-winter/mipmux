# Discovery prompt source and bindings

Discovery reads the operator's `discovery.promptTemplatePath` once per job. `prompts/discovery.md` is the shipped default; an installed copy is editable policy. Swift selects named sections and substitutes typed runtime values to compose the system policy and startup metadata. The Markdown contains the mipmux-facing tool examples and runtime guidance. Context assembly uses the numeric user budget; recipient compatibility belongs to delivery.

## Reference rendering

The reference was rendered from `Sources/RepoPrompt/Infrastructure/AI/SystemPromptService.swift` at RPCE commit `43a9c29d3894e4841d8cca4c75b45f7a68b3ecb3`, Git blob `4943690a86bf880ce9f5cb085e2e4f57211175e5`. The renderer executed the source's `discoverPrompt`, `mcpDiscoverPrompt` and supporting review-guidance functions with these inputs:

- `tokenBudget: 198500`, the scout allowance for a 200000-unit build after the single 1500-unit reserve. Jobs supply their captured numeric allowance.
- `agentKind: .codexExec`, for the restricted-tool workflow.
- `enhancementMode`: Rewrite, Augment and Preserve, each with separate fragments for its handoff step, success criterion, anti-pattern and checklist.
- `allowClarifyingQuestions`: enabled and disabled.
- Review guidance: absent, elected-target artifacts, explicit read-only Git with named roots, and explicit read-only Git with root lookup. Production binds the captured purpose and original task to the retained review-intent helper; the frozen Git target supplies authorization facts.
- `__SUPPORTED_LANGUAGES__` as a placeholder for the catalog of supported languages at runtime. Mipmux reports structural coverage through `get_code_structure` results.

Only external type/default/catalog definitions were supplied by the reference renderer; the prompt factory's policy text and branching were executed unchanged. The source text retains its punctuation and whitespace. The language catalog in production comes from the retained syntax engine. Pi exposes scoped context tools and configured HTTP MCP tools, not provider-native shell/filesystem tools, so every Pi provider uses the restricted-tool branch.

The native `renderDiscoveryPrompt` operation accepts admitted template text and captured mode, purpose/task, clarification, Git/root, budget and startup facts. `DiscoveryTemplate.swift` parses the finite format; `RPCEContextBuilderPrompt.swift` selects sections and formats values using the native language catalog and retained review-intent helper. One operation returns both system text and the complete startup message. Syntax rejection is a correlated domain result from rendering, after wire-field admission.

Startup framing retains `ContextBuilderAgentViewModel.makeUserMessage` ordering for the file map, current prompt, task-specific discovery instructions and rendered metadata. The template's startup guidance describes the selected full-file, slice or codemap representation. `test/fixtures/rpce-discovery-message/` retains original-source evidence; current conformance compares applicable no-overlay cases with guidance describing the selected full-file, slice or codemap representation. `scripts/generate-discovery-message-fixtures.mjs` regenerates those historical source fixtures. Pi receives the message followed by the captured observation in `mipmux_runtime`; the task and then any discovery hints are joined with two LF characters in the discovery instructions section.

RPCE supplies the configured budget after its host-side 1500-unit reserve. Mipmux supplies `max(0, request.budgetUnits - 1500)` as `DiscoveryInput.tokenBudget`; complete-packet measurement uses `request.budgetUnits`. The prompt reads the scout budget rather than deriving a budget from a receiving model.

## Template format

The first line is exactly `# mipmux discovery template v1`, terminated by LF. Each named section uses standalone delimiter lines:

```text
<!-- mipmux:section system -->
[section body]
<!-- mipmux:end -->
```

The complete file defines each required section exactly once. `system` holds the common policy and `startup.metadata` holds the complete startup metadata block. Each mode (`fullRewrite`, `augment`, `preserve`) defines `mode.MODE.handoff`, `mode.MODE.success`, `mode.MODE.antiPatterns` and `mode.MODE.checklist`. The remaining names are `codemode.tool`, `clarification.tool`, `clarification.guidance`, `clarification.approval`, `review.artifacts`, `review.readOnly`, `review.roots.named` and `review.roots.lookup`.

Definition order is independent of output order. Empty bodies are valid, including the shipped Preserve checklist. Body lines are joined with physical LF; the delimiter boundary contributes no automatic terminal LF. Leading/trailing blank body lines express the corresponding output newlines. CR characters, tabs, whitespace-only bodies and Unicode sequences remain literal. Outside sections, only blank separator lines are accepted.

Placeholders have the exact form `{{mipmux:NAME}}`. Common scalar names are `token_budget`, `supported_languages`, `question_timeout_seconds` and `halt_step`. Only `review.roots.named` may use `root_names` and `example_root_json`; the latter supplies a complete JSON string literal, including quotes.

The `system` section may insert `handoff`, `handoff_success`, `handoff_anti_patterns`, `handoff_checklist`, `codemode_tool`, `clarification_tool`, `clarification_guidance`, `approval_step` and `review_guidance`. Only `review.readOnly` may insert `review_root_guidance`. Other sections accept scalar placeholders only. Swift chooses the four mode fragments, inserts the codemode fragment when the session offers `codemode`, enables the three clarification fragments together, and selects artifact or read-only review guidance. Read-only review selects named-root guidance when roots exist and lookup guidance otherwise.

The parser reserves `<!-- mipmux:` and `{{mipmux`. Unknown, duplicate, missing, nested or unterminated sections and malformed, unknown or disallowed placeholders reject the file, including errors in inactive sections. Closing `}}` outside a reserved placeholder is literal JSON or prose. Inserted values are rendered once and never reparsed as template syntax. The format supports fixed section selection and typed insertion; it has no loops, includes or executable expressions.

## Clarification binding

Setting `ContextBuildRequest.clarification` selects the `ask_user` suffix in the tool list, clarification guidance and the step requesting approval of the selection. Its default timeout is 300 seconds. An enabled run exposes `ask_user`; the default MCP setting is disabled. Example calls use the public structured `questions` schema with question ID `response`. Operators can insert `question_timeout_seconds` when editing policy; the shipped text follows the source, which omits a numeric timeout.

`AskUserInput.swift` reuses the original parser, question models and `MCPAskUserElicitationBridge` conversions. It also returns normalized question fields for the MCP boundary. The installed MCP SDK uses multi-round-trip `input_required` results and cannot encode the source's free-text arrays or `uniqueItems` constraint. `src/mcp/question-form.ts` maps fields to collision-free indexed transport keys. Fixed-choice arrays use the SDK's multi-select form, and multi-select questions with custom answers use separate choices and custom-text fields. Responses are reconstructed under the original question IDs and checked against the original schema, including uniqueness, before native answer conversion. No question or answer policy is inferred from rendered prompt text.

A `context_job` wait returns these forms to clients that support them, and the question's original schema to other clients, which answer with `op: "answer"`. Job-owned deadlines, cancellation and response ownership apply across request retries. `test/clarification-mcp.test.ts` exercises real Pi dispatch and the current MCP protocol, including multi-select/custom answers, final approval, decline, timeout, form/job cancellation, client closure, answers from a client without forms and cross-job response rejection. The installation test exercises enabled interaction through the MCP server from the installed package and an external editable template.
